# Reviewing before merge

Decide whether a change is safe to ship by walking the review one section at a time: explore the diff, surface what was found, name the risks, run verification, deliver the verdict. The user holds product context (deliberate behaviour change? consumer used externally?) the AI can't infer from the diff — surface it through questions, don't assume.

**Announce at start:** *"Reviewing the diff against fresh test evidence."*

## Output discipline (mandatory)

Inherits `using-sumo-qa`: **output discipline** (never surface internal taxonomy labels — say *"behaviour change in pricing"*, not `Classification: business_logic_change`; cite a change-rule in plain English — *"the documented-inventory rule"* — never by echoing its YAML key), **output economy** (findings not framing; no preamble/self-narration; one question per turn; no closing pleasantries), knowledge-authority hierarchy, internal scaffolding stays internal, specialty-tool fit.

<HARD-GATE>
Do NOT deliver a verdict before running tests THIS turn. "CI was green earlier" is not fresh evidence. The only verdict source is the suite running RIGHT NOW against THIS diff, with actual pass/fail counts surfaced.
</HARD-GATE>

## The Iron Law

**NEVER CLAIM SAFE-TO-MERGE WITHOUT FRESH VERIFICATION EVIDENCE.** "All tests pass" is necessary but not sufficient — every named risk must also have a passing test covering it.

## When to Use

Triggers: *"review my changes"*, *"is this safe to merge"*, *"what could break"*, *"code review please"*, *"anything I missed in this diff"*. `sumo-qa-deciding-approach` routes here for `verify-existing` (config/trivial); larger reviews run here with broader scope.

## Checklist (in order; steps 1–4 are AI-only homework, no user questions; user confirmation gates steps 5+)

1. **Read the diff via host git tools** — `git diff` / `--staged` / `<base>...HEAD` per intent. Capture file list + line counts.
   - *Repo-map accelerator (optional):* `sumo_qa_analyze_diff_impact` scans live + persists a repo-map; returns changed/affected nodes, likely tests, risk surface (changed sources with no mapped test). NOT coverage evidence — `related_tests` are run-candidates, `risk_surface` candidate UNCOVERED anchors, never proof; never blocks. If `probable_mapping_gap` is true (tests exist but no links found — CamelCase/Kotlin), it's a *mapping* gap not zero coverage — confirm via the test tree. Fresh-run requirement unchanged.
   - *Context bundle (optional input):* if the host hands a bundle (issue/PR summary, changed files, test/CI evidence each with source+freshness, user constraints), PREFER it as a head-start: read via `sumo_qa_format_context_bundle` (pass live local head as `local_head_sha`). No bundle → direct inspection. Three rules: (a) **stale/unknown evidence is not fresh** — any field in the tool's `untrustworthy_evidence_fields` (freshness stale/unknown/absent) → re-run the suite this turn, never claim safety from it; (b) **call out conflicts** — on a `conflict` (bundle `head_sha` ≠ live head) say so and trust the live diff; (c) the bundle NEVER replaces the diff read (still do steps 1–2).

2. **Read the actual changed files** — not just hunks; surrounding code matters. Per file: identify the public surface that moved.

3. **Classify + load standards** — `sumo_qa_load_classifications()`, infer classification(s), then `sumo_qa_load_standards(...)` and `sumo_qa_load_rules(...)`. Note which rules apply. ("No standards apply" is wrong — every change has ≥1 applicable classification.)

4. **Adversarial discovery pass → 3–7 named risks anchored to file:line.** Codex-class defects ship past green suites because nobody swept the diff. Each hit = a named risk citing file + line + domain meaning (NOT generic "edge cases"/"untested paths").

   **First branch on diff shape.** If the diff is **test files ONLY** (no `app/`/`src/`/`lib/` runtime file — a `test_change`), runtime probes mostly don't apply → run the **test-only-diff probe (step 9)** instead; its findings ARE this turn's named risks. A green suite is NOT a pass for a test_change (a tautological assertion passes any impl). Do this BEFORE the verdict; then run runtime probes for any runtime file present.

   **Runtime probes** (code-shape signal → defect class to suspect):
   - **Reordered statements in a write/persist path** → intermediate state now observable/persisted; partial failure leaves invalid/partial state (rollback / data-loss).
   - **Removed/loosened/inverted guard or conditional** → the blocked path is now reachable; name what it exposes.
   - **A rollback/cleanup/undo path** → does it RESTORE overwritten/pre-existing state, or `unlink`/clobber it? Deleting a pre-existing destination is data loss, not rollback.
   - **A documented count/name/inventory, version bump, or generated artifact (manifest/lockfile/sidecar)** → search the supplied repo state repo-wide for stale copies of the old value; for generated files, was the generator re-run and output committed? (documented-inventory / generated-artifact drift — step 9).
   - **A file/path enumeration (`git ls-files`, glob, walk)** → does it include entries it must not — tracked-but-deleted, ignored, suffix-variant, hidden?
   - **A path check vs `cwd`/relative root** → should it anchor to repo/project root? cwd-relative checks are bypassable from a subdirectory (security boundary).
   - **A platform/OS branch (`sys.platform`, symlink-vs-copy, separators, spaces in paths)** → is every branch's inverse/cleanup symmetric and actually exercised?
   - **A widened type/schema (bare `dict`/`Any`/`object`, new optional union, relaxed validation)** → does it weaken a previously-constrained contract or published/derived schema?
   - **A declared invariant in a docstring/contract (`Never raises`, "always returns an error envelope", total-function promise)** → hold it against the ACTUAL signature and raise paths: the claim is violated if a REQUIRED arg (no default — for an MCP-registered fn the schema layer rejects an omitted required arg as a raise BEFORE the body's envelope branches), a bare `raise`, or an un-envelope'd error path can fire for the "invalid input" the contract promises to absorb. Name the contradiction at file:line (docstring invariant vs signature/raise).
   - **A retry/async/timeout/teardown/shutdown path** → idempotency across retries, poison-message parking, teardown-after-assert that can raise and error a logically-passing test (cleanup flakiness).
   - **A CI / merge-gate change (required checks, admin-merge, wait conditions)** → does it wait on ALL required checks (full matrix), or proceed before some finish?
   - **A weakened test assertion (substring/presence-only replacing exact/structural)** → would it still pass if the contract under test were removed? (tautology — a test-only SAFE-blocker).
   - **A matcher/parser over EXTERNAL output (regex/string match on subprocess/CLI text, an API response-shape assumption, another tool's file format, a committed fixture mimicking tool output)** → correctness depends on the REAL output of a tool/CLI/API the diff doesn't control. Green tests prove matcher LOGIC, not that the marker matches REAL output; a hand-authored fixture can be fiction (the `mutmut run` emoji-vs-`survived` miss). Name the external-contract dependency (external-contract probe — step 9). **Producer test (apply first):** fires ONLY when the value is produced by something the diff does NOT control (another tool/CLI/subprocess/API/foreign file). If the SAME change (or host) is its sole producer — code serialises its own envelope/marker and parses it back (self-format round-trip) — it is INTERNAL: raise NO external-contract risk, demand NO "real run" capture (ordinary internal risks like round-trip/charset/boundary may still apply). When INTERNAL, you MUST SAY SO explicitly (silent suppression insufficient): quote the self-produced value verbatim (e.g. `[sumo-qa:CODE]`), name the sole producer and same-module consumer, conclude the external-contract axis does NOT fire (2d row carries this).
   - **A stateful char-scanning parser tracking an open/close marker (fenced-code/heading indexer, bracket/quote matcher, comment/string tokenizer)** → does its close-test match the FULL opening marker, or only the marker CHARACTER? *Char-only fence tracking is the structural tell that LENGTH is not tracked* — a `` ``` `` close wrongly closes a `` ```` `` (4-tick) outer fence, so `## heading`-looking lines INSIDE the block get indexed (or real headings after it get skipped). This is state-transition testing (`sumo_qa_load_techniques`): a fence is a state, mis-tracking the close is the illegal transition. **"Verified correct" requires constructing the discriminating input, not asserting from a code read** (2b). The single DISCRIMINATING input for a length-not-tracked bug is a **variable-length nested fence — a 4-tick fence wrapping a 3-tick block**: length-aware keeps the outer fence open across the inner `` ``` ``, char-only closes it early. Prescribe THAT. Other fence cases are general CommonMark §4.5 edge cases — describe each by ACTUAL behaviour:
     - **OPENING fence** may be indented ≤3 spaces; ≥4 spaces is NOT a valid opening (reparsed as indented code block, ex.134). **CLOSING fence** also ≤3 spaces; a ≥4-space-indented close-looking line does NOT close and is NOT indented code — it stays as fenced-block CONTENT (ex.137). The in-fence indexer must still SKIP it as content; treating it as a close is the bug. Discriminates an impl that `lstrip()`s before the marker check.

     Until the variable-length nested fence is built and exercised, the parser is UNPROVEN — never COVERED from reading that the code "compares the fence char".

   **Discovery → verdict (pinned).** A defect this sweep surfaces that fresh tests don't cover is a NAMED RISK, mapped UNCOVERED (step 9) → SAFE-blocker → NOT SAFE. Do NOT demote a discovered latent defect to a "residual concern" under SAFE, and do NOT call it covered because a green test runs nearby — a happy fixture / empty-target ingest / repo-root run / single-OS leg does NOT cover the overwrite / deleted-entry / subdirectory / other-OS path. Treating it as coverage is the bypass this pass exists to prevent.

   **Skip the sweep ONLY for the trivial-change exemption** (genuinely non-executable diffs — docs, tool-only/static config with no runtime consumer); running it there manufactures phantom risk (negative-control failure). The sweep keys on **executable behaviour, not path prefix**: an executable hook/script/automation under `.claude/hooks/`, `scripts/`, or any non-`src/` location gets the same mandatory sweep as a library module.

5. **Confirm scope, only for AMBIGUOUS parts** — short paragraph naming files, line counts, what the change does in domain terms. Then ONE focused question for what the diff couldn't reveal (e.g. *"is this consumer external — coordinate the contract bump?"*). Nothing ambiguous → skip the question. (Don't ask which framework / where tests live — read the repo.)

6. **Present named risks, ask after** — the 3–7 risks anchored to file:line:

   **Technique-keyed failure-mode hints (pinned).** When a risk maps to a named black-box technique, ground it in that technique's catalogued failure modes (`sumo_qa_load_techniques`), not per-AI judgment, and name the one in play: precision/recall on a keyword/substring matcher → *equivalence partitioning* (substring/token confusion — `unlocked` matches `locked`, `concurrency` matches `currency`; overlapping classes; missing empty-input class); limit/threshold/off-by-one → *boundary value analysis* (both-sides + just-inside-vs-just-outside, `<` vs `<=`); multi-condition rule → *decision tables* (missing rule row / absent default). If the technique isn't in the loaded catalogue, say so — don't confabulate.
   Ask: *"do these match how you'd describe the risks? add / remove / refine?"* Wait.

7. **Run the suite — show actual output** — host runner. Surface total/passed/failed/skipped/duration. Failures → name them. No verdict on partial output.

8. **Run targeted tests around changed files** — e.g. `pytest tests/test_<module>.py -v`. Confirm closest neighbours green; surface the count.

9. **Map risk coverage.** For each named risk, cite the fresh test that demonstrably exercises that exact failure path (file + fully-qualified test + verbatim assertion/condition), or mark UNPROVEN/UNCOVERED. Never infer coverage from shared name/domain. A risk with no covering test is a SAFE-blocker.
   - **Re-anchor first.** Bare-name risks (*"Auth Session Bypass"*) → locate the anchor file in the diff before mapping (*Auth Session Bypass* → `app/auth/session.py:33`). `sumo_qa_query_repo_map` helps locate a RUNTIME risk's anchor/candidate test by path/name (a test counts only once in THIS run with a verbatim assertion); it does NOT consolidate inventory drift (each stale path gets its own 2a row).

A `tests/billing/` test cannot cover an `auth/session.py` risk via *"indirectly/implicitly validates"* — forbidden hallucinated bridges → mark UNCOVERED when paths don't match. If the fresh run loaded no test for a changed file's module, every risk anchored there is UNCOVERED however green the rest is.
   - **Integration/e2e exception:** tests under `tests/integration/` or `tests/e2e/` MAY cover any module risk, but only if the cited assertion verbatim invokes (or asserts a property of) the risk's anchor function; "the integration suite passed" without naming that assertion is the same hallucinated bridge.

Its evidence is REAL captured output, never a `tests/<module>/` test. A genuine parsing risk the diff's own code path can hit is fair; speculative variant-hunting on a discharged contract is not. Plus a matcher-coverage check: name each test's oracle/matcher, enumerate the input *shapes* it must catch, confirm each has a discriminating case — a matcher that silently under-matches a shape (singular-vs-plural false-negative class) is a hole even when present assertions are sound. These findings ARE the named risks. A test whose assertion restates production code or passes against a broken impl (a tautology re-deriving "expected" from the SUT — `result = add(2,3); assert add(2,3)==result`; expected must be derived INDEPENDENTLY of the SUT), or a regression/contract test with no evidence it fails on the pre-fix/drift state → SAFE-blocker → `NEEDS WORK`/`NOT SAFE`, naming the vacuous assertion. Search the supplied ground-truth context (any `rg`/grep listing, "Other repo state" section) for the OLD value; each path = a separate UNCOVERED anchor with its own ledger row (2a). Generic guidance / anchoring only on the obvious doc / naming one stale path = UNCOVERED. Zero stale paths in context → say so explicitly; do NOT silently default to "covered".

When the host supplies ACs (user pastes them, or context bundle), check EACH vs diff + fresh test evidence (AC→evidence, the step-9 traceability move). **Surfacing every supplied criterion is MANDATORY, not verdict-conditional:** emit one AC line per criterion with classification AND cited anchor — INCLUDING MET ones on an all-MET SAFE path. The test must prove what the criterion *says*, not every downstream nuance: if it's "returns the caller's remaining quota" and a fresh test asserts the endpoint returns `remaining`, that's MET — a separately-unproven nuance (per-token discrimination) is a named *risk*, NOT an AC downgrade. Don't raise the bar above the wording.
   - **UNMET** — nothing in the diff satisfies it, or it's contradicted; SAFE-blocker.
   - **UNVERIFIED** — the diff plausibly addresses it (implementing change exists) but NO fresh test exercises the criterion's OWN behaviour this turn (only an adjacent/lower-level unit ran — e.g. a backoff-delay calculator when the criterion is end-to-end retry-on-5xx). For "the behaviour was never driven," NOT "asserted but one nuance unproven." SAFE-blocker until proven.

### Review-feedback memory (advisory hints only)

A team can promote a recurring lesson into an EXPLICIT, user-confirmed local memory (`sumo_qa_capture_review_feedback`, under the user-pack `feedback/` subdir). When present, consult it as a HINT that sharpens step 4 — never a blocker or authority. Apply a stored lesson only when its `trigger_signal` matches THIS diff's change shape; surface it SEPARATELY as its own labelled line, QUOTING the matched `trigger_signal` and `recommended_probe` VERBATIM (paraphrase the reviewer can't trace = grounding failure): *"advisory hint from saved review feedback (trigger: <trigger_signal>): <recommended_probe>"*, distinct from catalogued techniques/loaded change-rules. A matched hint becomes an ordinary named risk through the coverage ledger; it NEVER overrides a canonical classification or change-rule. Absent/empty → say so in one line (*"no saved review feedback supplied — advisory-hint check skipped"*) and run the normal sweep; NEVER invent/infer/recall a hint. Do NOT auto-capture: saving is a separate, explicit, user-confirmed step storing only the user's own short summary (never a raw diff/secret/code snippet/pasted issue body).

### Verdict-format discipline

The verdict line is the LAST line.

**What counts as a runtime change (behaviour, not path prefix):** any diff touching **executable code with a behavioural surface** — code that runs and can branch, parse a command, gate an action, transform input, or persist state, producing a wrong observable result. Keyed on what the file *does*, NOT on `app/`/`src/`/`lib/` location. Includes executable code OUTSIDE those dirs — a hook under `.claude/hooks/`, a `scripts/` script, a `.claude/` automation/generated runner, a CI/release workflow shell step, a Makefile/justfile recipe, a git hook — the moment it carries branching or command logic. A pure metadata bump (version string, name list) stays the inventory-drift rule's, not runtime. For a runtime change, BEFORE the verdict emit, in order:

1. Each named risk by exact name, one per line (`Risk 1: Auth Session Bypass`).
2. A coverage-ledger line per risk in this exact shape:
   `Risk: <exact name> | Anchor: <diff file:line> | Required test path: <test dir covering this anchor — tests/<module>/ for app/<module>/; for an executable anchor outside a source dir, the sibling test dir mirroring it, e.g. tests/hooks/ for .claude/hooks/, tests/scripts/ for scripts/> | Fresh matching tests: <fresh tests whose path starts with the required path, as fully-qualified `<file>::<test>` IDs, or NONE> | Coverage: <COVERED (cited test + verbatim assertion) | UNPROVEN | UNCOVERED>`
   - `COVERED` only when a fresh path-matching test quotes a verbatim assertion/condition exercising the failure mode — path prefix is necessary, not sufficient.
   - Risks whose name/anchor/failure-mode contains **Retry, Duplicate, or Idempotency** require an assertion showing the operation invoked MORE THAN ONCE (two calls / a loop / a call-count or idempotency-token assertion across attempts). **Concurrent, Race, or Lock** require overlapping execution (threading / `asyncio.gather` / `concurrent.futures`, or an explicit interleave). A single non-overlapping invocation — even one that raises — proves none of these → UNPROVEN.
   - `Fresh matching tests: NONE` → UNCOVERED; never cite non-matching tests as indirect evidence.
   - `COVERED BY VERIFICATION` is reserved for docs/config-only anchors; runtime anchors MUST NOT use it.
   - **2a. Inventory-drift extension.** For an inventory-drift risk, the risk row is not sufficient. Emit ONE additional row per stale path the supplied ground-truth context names (never crammed into one row or shoved into the risk row's `Required update:`), in this exact shape (value pair inline):
     `Inventory drift anchor: <path>:<line> (<old> → <new>) | Required update: this file | Diff updated it: <YES if the diff touches this exact path; NO otherwise> | Coverage: <COVERED if the diff updates this exact file; UNCOVERED if not>`
     Each UNCOVERED row is a SAFE-blocker. The verdict line names every UNCOVERED stale path explicitly — not "documentation needs updating". Zero stale paths supplied → `Inventory drift anchor: NONE supplied | Coverage: N/A` (never silently default to covered). *Contrast:* two stale paths `docs/INSTALL.md:17` + `.github/ISSUE_TEMPLATE/qa_output_quality.yml:22`, `28`→`29` → BAD = one crammed row anchored on the obvious doc, no `(28 → 29)` (SHAPE FAIL); GOOD = one row per path with `(28 → 29)` inline and `Diff updated it: NO | Coverage: UNCOVERED`.
   - **2b. UNPROVEN-escalation extension (pinned).** A `Coverage: UNPROVEN` row is NOT dischargeable by noting the risk as a "residual concern" — that escape hatch shipped a known precision/recall trade-off as SAFE. Every UNPROVEN row MUST additionally emit ONE of these two lines (exact shape) before the verdict; until one is present the row is a SAFE-blocker:
     - **Prescribed (preferred):** name a concrete discriminating input — one input broken and correct impls handle DIFFERENTLY (broken gives a wrong observable result, correct the right one) — and add a regression test asserting the CORRECT behaviour before SAFE. State the behaviour contrast: the added test asserts the right result, so it is RED against the broken impl and GREEN once fixed.
       `UNPROVEN escalation: <risk name> | Discriminating input: <the input> | Broken impl does: <wrong observable result> | Correct impl does: <right result> | Required before SAFE: add a test asserting the correct result to <tests/<module>/...>`
       Anchor the input in the technique's catalogued failure mode where one fits (substring/token confusion → an input containing the keyword but not in the class, e.g. `unlocked` wrongly matched by a `locked` matcher; boundary → the boundary / just-inside / just-outside value distinguishing the OBSERVED comparator, e.g. the limit value itself for a `<` vs `<=` bug, not a far-outside value; decision-table gap → the unenumerated combination). An input both impls handle the same is NOT discriminating — reject it. This row stays a SAFE-blocker until the test is added and green in a fresh run — it RAISES the bar, doesn't grant SAFE on its own.
     - **Deferred (only with the failure mode named):** if the user explicitly defers, the deferral must NAME the accepted failure mode, not "residual precision":
       `UNPROVEN deferral: <risk name> | Accepted failure mode: <named mode, e.g. substring/token confusion> | Acknowledged by: <user> | SAFE-blocker: YES (always)`
       An acknowledged deferral records the user's accepted risk; it never makes the verdict SAFE while the risk stays UNPROVEN — the verdict remains NOT SAFE and names the accepted residual. Only a prescribed input added + green (→ PROVEN) clears UNPROVEN.
     A bare `Coverage: UNPROVEN` row with neither line is a discipline violation. Raises the SAFE bar on UNPROVEN risks only.
   - **2c. External-contract extension (pinned).** For an external-contract risk, emit this row INSTEAD of the path-keyed row (`Required test path` does not apply):
     `External-contract anchor: <file:line> | External source: <tool/CLI/API> | Real-output evidence: <captured fixture + provenance/capture command, or NONE> | Coverage: <COVERED (real-run-traceable fixture cited) | UNPROVEN (hand-authored/no real-run traceability)>`
     Documented real-run capture → COVERED, SAFE-eligible. Hand-authored, no traceability → UNPROVEN, SAFE-blocker. Never emit `Required test path: tests/<module>/` for an external-contract risk.
   - **2d. Internal/self-produced declination (pinned).** When the external-output probe resolves INTERNAL (producer test), emit so the true-negative is on record:
     `External-contract axis: NOT FIRED (internal/self-produced) | Value: <verbatim self-produced value, e.g. [sumo-qa:CODE]> | Producer: <fn/module> | Consumer: <fn/module, same change> | No external source: confirmed`
3. `Touched files:` citing every diff path verbatim (e.g. `app/auth/session.py, tests/billing/test_checkout.py`).
4. `Change shape:` one phrase anchored to touched files (e.g. `auth predicate + billing checkout ordering, both runtime`).
5. The verification command, quoted verbatim.
6. The test counts verbatim (`X passed, Y skipped, Z failed`).
7. **AC lines (whenever ACs were supplied).** One line per supplied criterion, regardless of verdict — the MET ones too, never dropped on an all-MET SAFE path:
   `AC<n>: <criterion text> | Classification: <MET | UNMET | UNVERIFIED> | Anchor: <diff file:line + fully-qualified fresh test::name and verbatim assertion for MET; the criterion / the missing behaviour for UNMET/UNVERIFIED>`
   Every UNMET/UNVERIFIED line is a SAFE-blocker. No criteria supplied → emit `No acceptance criteria supplied — AC-coverage check skipped; verdict rests on risk coverage.` instead.
8. **Verification-evidence lines (step 9).** Emit the lines that apply, each a SAFE-blocker unless DISCHARGED:
   - Surface verifier (always, on a runtime/skill/eval change): `Surface verifier: <verifier — the eval's FULL config path quoted verbatim from the diff/context, e.g. tests/evals/promptfoo/skill-<area>-<feature>.yaml (never a truncated stem) | NONE identifiable> | Ran: <YES (runtime/env/key/scope/tree cited — eval-surface: Node 24 + key) | NO | WRONG CONTEXT (which)> | Combined-tree (if sibling PRs co-edit): <YES | NO | N/A> | Status: <DISCHARGED | N/A (no identifiable verifier surface — non-blocking) | UNVERIFIED (surface verifier) — SAFE-blocker>`
   - Feature flow (when one exists): `Feature flow: <the realistic UI/API/CLI/worker/artifact path | NONE identifiable> | Exercised end-to-end this turn: <YES (fresh path-matching test cited) | NO (only <lower-level unit> ran)> | Status: <VERIFIED | UNVERIFIED (feature flow) — SAFE-blocker>`
   - Guard coverage (when the change ADDS a regression guard / "do X but NOT Y" rule): `Guard added: <the guard> | Eval exercises BOTH directions: <YES (positive + discriminating true-negative/over-trigger seed cited) | NO (one-sided)> | Status: <COVERED | UNCOVERED — SAFE-blocker>`
   - A/B validity (when an eval-driven skill change ships a load-bearing A/B eval): `A/B control: <the .ab.yaml> | A0 structurally cannot pass via pre-existing rules: <YES (rubric PASS needs only-new-text) | NO/UNKNOWN — single A0-FAIL is variance> | Rubric credits only discriminating inputs: <YES | NO (name the non-discriminating one)> | Status: <LOAD-BEARING | UNPROVEN — SAFE-blocker>`

A runtime verdict emitted before items 1–6 (plus 7 when ACs are present, 8 when the change touches a verifiable surface/feature flow/guard/eval-driven skill) is a discipline violation.

**Trivial-change exemption (pinned):** for **genuinely non-executable diffs**, NOT "anything outside `app`/`src`/`lib`". Qualifies only when it touches solely docs (`docs/`, markdown), static/inert config (YAML/TOML/JSON read as data — formatter/linter ignore lists, editor config), or files with **no executable behavioural surface**. Path is irrelevant — an executable hook/script/automation under `.claude/hooks/`/`scripts/`/`.claude/` is runtime despite sitting outside source dirs → does NOT qualify (full sweep + ledger). When it DOES qualify: SKIP item 2; the verification command (linter/formatter/build) IS the coverage → mark anchors `COVERED BY VERIFICATION`. Items 1, 3, 4, 5, 6 still required. `Touched files:` and `Change shape:` mandatory in BOTH modes; citing the verification command's file argument does not discharge `Touched files:`.

**Test-only-diff (test_change) discipline (pinned):** diff touches ONLY test files (no runtime file) → the runtime ledger (item 2) does NOT apply, but it is NOT trivial and a green suite is NOT a pass. Before the verdict emit, per new/changed test, one probe line:
`Test probe: <test name> | Discriminates broken→fixed? <YES (the assertion a broken impl fails / for a regression, cited RED-on-pre-fix evidence) | NO (the vacuous assertion named verbatim — self-referential expected, type-only, restates prod code)> | <PASS | SAFE-blocker>`
Any `NO` line is a SAFE-blocker → verdict `NEEDS WORK`/`NOT SAFE`, naming the vacuous assertion. Items 1 (named risks = probe findings), 3, 4, 5, 6 still required; item 2 is replaced by these probe lines.

10. **Deliver verdict + residual concerns** — `SAFE TO MERGE` | `NOT SAFE TO MERGE` | `NEEDS WORK` with concrete evidence (counts, coverage map, rule citations). SAFE only if (a) suite green now, (b) every named risk has ≥1 fresh test demonstrably exercising that exact path (not a tangentially-named one), (c) no loaded rule violated. **If ANY named risk is UNCOVERED or UNPROVEN → verdict MUST be NOT SAFE — no exceptions, even on a fully green suite.** The ONLY way an UNPROVEN risk becomes SAFE-eligible: add its prescribed 2b discriminating input and run it GREEN (→ PROVEN/COVERED). A deferral never yields SAFE (named-failure-mode deferral is better-documented but still NOT SAFE, naming the accepted residual; a bare UNPROVEN row is a violation). **(d) When ACs were supplied, EVERY criterion must be MET; ANY UNMET or UNVERIFIED is a SAFE-blocker → NOT SAFE, no exceptions — the verdict names each.** **(e) Verification-evidence: ANY of UNVERIFIED (surface verifier), UNVERIFIED (feature flow), UNCOVERED guard, or UNPROVEN A/B control is a SAFE-blocker → NOT SAFE — cleared only by running the verifier correctly (right runtime/env/key/scope, combined-tree for sibling PRs), exercising the flow end-to-end, adding the missing-direction guard seed, or proving the A/B load-bearing; NEVER by weakening the verifier or rubric.** Always list residual concerns, even on SAFE.

   **The two-pass split (pinned).** In `/work-issue` this review is pass 1; an adversarial codex pass runs after. The catch this skill must NOT outsource: when it can name a precision/recall risk and the technique has a catalogued failure mode, it prescribes the discriminating input ITSELF (step 9 / 2b) — not deferred to codex. Pushing the catch here is what makes the review scale when codex isn't available (CI-only runs, limited tokens). Codex remains a second independent check, never the only place an UNPROVEN risk gets a discriminating input.

### Risk-to-test ledger appendix (optional, structured)

The prose verdict is the deliverable; never replaced. When the user wants a paste-into-PR artifact (*"give me the ledger"*, *"export the risk map"*), project the SAME named risks + coverage map via `sumo_qa_format_risk_ledger` and append it BELOW the verdict (never in place). The tool is file/format plumbing: YOU identify the risks, it validates and renders. One row per risk with `evidence_status` from this run — `passing` (a fresh path-matching test quotes the assertion), `failing` (fresh test red against this risk), `planned` (no fresh test yet — UNCOVERED/UNPROVEN), `stale` (a prior pass no longer reflecting the diff, e.g. an `xfail` pinning old behaviour), `accepted_residual`. Set `residual: blocker` for every UNCOVERED/UNPROVEN high-risk row; the tool's `uncovered_blocker_count` must be 0 before any SAFE verdict. Optionally link `repo_map_node_id` when a repo-map is loaded (a missing repo-map is weaker evidence, never a blocker). Skip the appendix for trivial reviews.

**Render as the markdown table the tool returns** (never a JSON blob), columns exactly: `| Risk | Statement | Source | Test / check | Evidence | Residual |` (one row per risk; `Evidence`=`evidence_status`, `Residual`=residual decision; `Test / check`=covering test id or a `planned: …` phrase; `Source`=file:line). **EVERY cell filled — `Residual` never blank:** covered/passing → `accepted` (or `mitigated`); uncovered/unproven high-risk → `blocker`; unsettled → `open`. No tool → emit this shape by hand. Example:
`| R1 | Invalid-amount now returns 422 not 500 | services/billing/refund.py:47 | tests/billing/test_refund_api.py::test_invalid_amount_returns_422 | passing | accepted |`
`| R2 | Idempotency key derivation moved → double refund on retry | domain/Refund.kt:18 | planned: re-invoke refund after partial failure, assert at-most-once | planned | blocker |`

**AC-coverage view (same schema, no new tool).** The per-criterion AC lines in the verdict (item 7) are mandatory whenever ACs are supplied — this appendix is only the paste-into-PR projection, never a substitute and never the trigger for surfacing MET criteria. When ACs were supplied and the user wants the artifact, project the AC map through the SAME `sumo_qa_format_risk_ledger` as a second table below the risk ledger — one row per criterion: `risk_id`=`AC1…`, `risk`=criterion text, `source_anchor`=diff file:line satisfying it (or AC text when unmet), `test`=covering fresh test id or `planned: …`, `evidence_status`=`passing` (MET) / `planned` (UNVERIFIED or UNMET), `residual`=`accepted` (MET) / `blocker` (every UNMET/UNVERIFIED). `uncovered_blocker_count` enforces the AC gate the same way — 0 before SAFE. Example:
`| AC1 | Skill checks each host-supplied criterion vs diff + fresh tests | skills/sumo-qa-reviewing-before-merge/SKILL.md:88 | tests/evals/promptfoo/skill-reviewing-before-merge-ac-coverage.yaml::ac-unmet | passing | accepted |`
`| AC2 | Refuses SAFE while any criterion is UNMET | step 10(d) | planned: scenario asserting NOT SAFE on an unmet AC | planned | blocker |`

## Red Flags — STOP and rework

| Thought | Reality |
|---|---|
| "Looks good" / "CI was green an hour ago" | Not fresh evidence. Run the suite now. |
| "Trivial change, skip the sections" | The Iron Law has no trivial exemption for the walk; review can be short, every section gets confirmation. |
| "Skip tests — they're slow" | Then you can't claim safe-to-merge. Slow tests are still the verdict source. |
| "All tests pass, so SAFE" | Necessary, not sufficient. Each named risk needs a covering test. |
| "Latent issue but tests green — SAFE with a residual note" | The sweep's hits are NAMED RISKS, not residual notes. A discovered defect fresh tests don't exercise = UNCOVERED = NOT SAFE. |
| "Path covered but no assertion hits the failure mode — note UNPROVEN, ship as known trade-off" | The exact bypass 2b closes. Prescribe a discriminating input (e.g. `unlocked` wrongly matched by a `locked` matcher) and require it before SAFE. Only adding it + green clears UNPROVEN; a deferral stays NOT SAFE; a bare UNPROVEN row never reaches SAFE. |
| "Codex will catch the discriminating input later" | Don't outsource. When you can name the risk and the technique has a catalogued failure mode, YOU prescribe the input — codex isn't there in CI-only runs. |
| "The fence parser compares the fence char — verified correct" | Comparing the CHAR only is the tell length isn't tracked — the defect, not proof. UNPROVEN until you build the discriminating input: a 4-tick fence wrapping a 3-tick block. `~~~`-vs-backtick and unclosed-at-EOF don't discriminate the char-stored bug — don't cite them as the discriminator. |
| "Clean refactor — skip the discovery sweep" | Mandatory for any runtime diff. cwd bypass, rollback data-loss, schema widening, partial CI gate hide in clean diffs and pass green suites. Only non-executable diffs (docs/static config) are exempt. |
| "Hook/script under `.claude/hooks/` or `scripts/` — trivial, skip" | Runtime keys on executable behaviour, not path prefix. Branching/command-parsing logic = runtime wherever it lives; full sweep + ledger. Echo-token / flag-arity / quote-splitting defects are the sweep's target. |
| "Matcher green, so parsing the tool's output is covered" | Green proves matcher LOGIC, not that the marker matches REAL output. Hand-authored fixture, no real-run traceability → UNPROVEN, NOT SAFE; covered only when it traces to a real/minimal run. Don't over-trigger on internal values or re-demand a capture the context already supplies. |
| "External-contract tests live at `tests/test_x.py` not `tests/<module>/`, so UNCOVERED" | Path rule does NOT apply to external-contract risks — evidence is real captured output. A real-run-traceable fixture is COVERED wherever its tests sit. |
| "Real-run fixture covers it — but what about emoji/locale variants?" | Speculative variant-hunting on a discharged (COVERED) external contract is over-trigger. The fixture proves the format for the cases the diff handles. |
| "It's self-produced, so I'll just not raise the risk" | Declining silently fails grounding. State it: quote the value, name producer and same-module consumer, conclude no external contract (2d). |
| "Diff is only tests — SAFE once green" | A test_change has its own probe. Green proves nothing if the assertion is a tautology or the matcher under-matches a shape. Vacuous = NEEDS WORK. |
| "No standards apply" | Re-classify. Every change has ≥1 applicable classification with loaded rules. |
| "List risks AND deliver verdict in one message" | Gate. The user's correction on the risks shapes the verdict. |
| "Ask which framework / where tests live" | Read the repo — sibling files answer it. |
| "Residual concerns: none" | Every change has them. None = you didn't think about what could still go wrong. |
| "Tests green, risks covered — SAFE, though one AC isn't delivered" | Green + risk-covered answers "correct code", not "the right code". An UNMET/UNVERIFIED supplied AC is a SAFE-blocker like an uncovered risk — NOT SAFE until met with cited evidence. |
| "No ACs pasted — skip silently" | Say so in one line, fall back to risk-coverage. Silent skip hides the unanswered right-code question; fabricating criteria is worse. |
| "The host should fetch the issue's ACs" | Never. Host-neutral: the host SUPPLIES criteria; the skill never calls `gh`/a tracker/an API. |
| "Per-file review, codex, CI all green — SAFE" | None exercise the changed behaviour. A relevant verifier (promptfoo eval, fixture/parser corpus, contract test, smoke probe) that did NOT run — or ran with wrong runtime/env/key/scope/tree — is UNVERIFIED (surface verifier), a SAFE-blocker. Eval-surface skill change → promptfoo with Node 24 + the configured key. |
| "Each sibling PR's eval passed in isolation — SAFE to merge the set" | Per-branch-green ≠ combined-green when siblings co-edit one surface. Require the verifier on the COMBINED tree (3/3 per-branch → 1/3 combined). |
| "A unit test exercised the new code — SAFE" | A unit running ≠ the primary FEATURE FLOW. Closest realistic UI/API/CLI/worker/artifact path never driven end-to-end → UNVERIFIED (feature flow), a SAFE-blocker. Don't over-fire when a fresh path-matching test genuinely drives the flow. |
| "The new guard is described and plausible — validated" | Described ≠ tested. COVERED only when its eval has a discriminating true-negative/over-trigger seed a guard-violating reviewer would FAIL. One-sided positive-only → UNCOVERED, SAFE-blocker. |
| "A/B shows A0 FAIL → A1 PASS, so the new text is load-bearing" | One A0-FAIL is variance, not isolation. A0 must be structurally INCAPABLE of passing via pre-existing rules; a lift explainable by a pre-existing rule is UNPROVEN. Apply 2b to the RUBRIC: a credited "discriminating" input must actually discriminate the seed defect. |
| "Fresh test doesn't prove every AC nuance — mark UNVERIFIED to be safe" | If a fresh path-matching test asserts the criterion's STATED behaviour, it's MET — the unproven nuance is a separate named risk. UNVERIFIED is only for when the criterion's behaviour was never driven. Over-firing UNVERIFIED is a SHAPE FAIL. |

## Examples

**Good (explore → confirm scope → risks → verdict, one section per turn):**
> User: "review my changes, is this safe to merge?"
> AI (scope): *"3 files: `api/refund.py` (+38/-4), `domain/Refund.kt` (+12/-2), `tests/test_refund_api.py` (+25/-0). Response shape + amount calc moved; `tests/contracts/refund_v1.json` untouched. Consumer external or internal-only?"*
> *(risks → tests → coverage map → verdict, one section per turn)*

**Bad (single-shot verdict):**
> AI: *"Looks straightforward — mostly internal refactor. Should be fine to merge. Maybe run CI."* — No fresh test evidence, no risk anchoring, no standards check. Iron Law violated.
