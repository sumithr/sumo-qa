# Reviewing before merge: security-relevance probe

Lazy module of `sumo-qa-reviewing-before-merge` (load via `sumo_qa_load_skill_context` with `mode="module"`). **Load when:** the diff touches an auth/authorisation guard, secret or token handling, input sanitisation, rate limiting, audit logging, or a security-relevant config/dependency movement. **Extends:** checklist step 4 (adversarial discovery pass) and the step-9 coverage ledger. The root's Iron Law, verdict gate, and output discipline apply unchanged.

## The security-relevant surface probe (step 4)

- **A security-relevant surface (auth/authorisation guard, secret/token handling, input sanitisation, rate limiting, audit logging, or a security-relevant config/dependency movement)** → run the grounded security-relevance pass from `using-sumo-qa`. A removed/loosened/inverted authorisation guard, a missing guard on a newly-added endpoint, a token-validation or expiry change, or unsanitised input reaching a sink is a CONCRETE security failure mode — name it (e.g. *"any authenticated user can read any document — ownership guard removed"*) and anchor it to the changed `file:line`. Then MAP IT THROUGH THE STEP-9 COVERAGE LEDGER like any other named risk: if NO fresh test exercises the security failure path it is UNCOVERED (a SAFE-blocker), and you then CLOSE it with the concrete remediation next action stated imperatively — the negative-path test phrased as the failing assertion it would add (*"add a test: a non-owner `GET /documents/{id}` returns Forbidden"*, *"add a test: a replayed/expired token is rejected"*), PLUS the review/static/dynamic/config/dependency check or `sumo-qa-security-testing` handoff the gap warrants. If a fresh path-matching test ALREADY exercises that failure path, it is COVERED like any other risk and is NOT blocked. Naming only the coverage hole (*"no test covers non-owners"*) is NOT enough — prescribe the action that closes it, exactly like the 2b prescribed-discriminating-input rule. It flows through the EXISTING `security_change` classification + loaded rules — no parallel taxonomy, no vulnerability-checklist dump, no vendor/tool-name dump. If the diff has NO grounded security surface, do NOT invent a security risk (the negative-control failure mode).
