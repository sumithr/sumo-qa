# Reviewing before merge: mirrored dependency constraints

Lazy module of `sumo-qa-reviewing-before-merge` (load via `sumo_qa_load_skill_context` with `mode="module"`). **Load when:** the diff adds, removes, floors, ceilings, pins or otherwise changes a dependency, tool or runtime constraint, runtime or trivial diff alike; load `inventory-drift` with it. **Extends:** checklist step 4 (discovery), step 9 (`inventory-drift`'s 2a rows) and Verdict-format item 8. The root's Iron Law, verdict gate, and output discipline apply unchanged.

## Mirrored-constraint probe (steps 4 and 9)

**Mirrored-constraint probe (pinned).** When the diff adds, removes, floors, ceilings or pins a dependency, tool or runtime constraint, the same constraint is often copied into an isolated environment the application suite never runs, so a green suite proves nothing about it. Search by the dependency's identity, classify each occurrence before judging it, and name every stale mirror as its own 2a row plus the exact command that runs its environment's own install/smoke check. Run it even under the trivial-change exemption: a manifest-only bump is exactly where the stale mirror hides.

1. **Search by identity.** Search for the canonical package/tool name and its spelling variants (`-`/`_`, case), not only the old version string. Check every applicable location: manifests, extras/groups, lock and constraints files; pre-commit/pre-push hook `additional_dependencies` and other isolated hook environments; CI install commands, setup-action versions and tool pins; Docker/devcontainer base-image tags; bootstrap, release, build and tox/nox scripts. The list is a floor, not exhaustive. A search that skipped hidden files (`.pre-commit-config.yaml`, `.github/`, `.devcontainer/`) is incomplete: say so.
2. **Classify before judging.** Give each occurrence one relationship: exact mirror, compatible range for a different supported runtime, deliberately independent environment (a documented reason), generated lock/resolution, or prose only (changelog, ADR, release notes). Only a stale exact mirror becomes an anchor. A compatible range only has to stay compatible; an independent environment keeps its documented reason; a generated lock is judged by its resolved version; a historical record states what was true then, so it gets no 2a row, no residual note asking to refresh it, and is never rewritten.
3. **Compare semantics, not text.** `<3,>=2.4` and `~=2.4` are both compatible with `>=2.4`: different syntax, order, or a narrower cap in another environment is not drift, and a release that does not exist yet is no present defect, so never demand one shared upper bound. A mirror is stale only when its range still admits versions the diff excludes, or excludes the versions the diff requires. The same test runs the other way: the diff's own uncapped constraint is not stale or risky beside a capped hook or CI pin, since each environment's own run shows what resolves today. A risk that needs a future major release to exist is speculation, not a named risk or a residual.
4. **Anchor each stale mirror.** Each gets its own `inventory-drift` 2a row with the constraints as the value pair, e.g. `Inventory drift anchor: tox.ini:12 (>=2.0 → >=2.4) | Required update: this file | Diff updated it: NO | Coverage: UNCOVERED`.
5. **Verify each isolated environment.** Fixed text does not prove the environment resolves and runs, so each isolated environment the diff changes or must change gets its own Verdict-format item-8 line, UNVERIFIED and a SAFE-blocker until its own install/smoke run is supplied fresh; the application suite's run never discharges it. The verifier field is the command someone runs to clear it (the hook run after its environment rebuilds, the image build, the CI install job), never a description of the environment:
   - BAD: `Surface verifier: the mypy hook environment | Ran: NO | Status: UNVERIFIED (surface verifier), SAFE-blocker`
   - GOOD: `Surface verifier: pre-commit run mypy --all-files (hook environment rebuilt) | Ran: NO | Status: UNVERIFIED (surface verifier), SAFE-blocker`
   The verdict line names that command as what clears the blocker, beside the file update.

**No mirror to fix (pinned).** When the search finds no second occurrence, or only compatible, independent, generated or prose ones, record each relationship in one line and raise no synchronisation requirement: no 2a row, no named risk, no residual asking to align or refresh them. Manufacturing one is the over-trigger this probe must not commit. The root still needs one concrete `Residual concerns:` item: take it from an unexercised code path or input, never from differing caps, syntax or history among compatible occurrences.

## Red Flags

| Thought | Reality |
|---|---|
| "The suite is green, so the dependency bump is proven" | The suite ran in one environment. A hook, image or CI job that keeps its own copy of the constraint is unverified until its own run. |
| "The hook says `<4,>=3.1` but the manifest says `>=3.1`: inconsistent, and 4.0 could break the uncapped one" | Compare semantics. Both admit what the diff requires and exclude what it forbids; a cap in one environment is not drift, and 4.0 does not exist yet. Cap neither side. |
| "I need a residual concern; the CI pin is tighter than the manifest, so I'll suggest aligning them" | That is the manufactured sync requirement again, moved into the residual line. Name an unexercised code path or input instead. |
| "The changelog still says the old version: stale" | A changelog or ADR records history. Leave it as written. |
