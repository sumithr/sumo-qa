# Reviewing before merge: optional context inputs

Lazy module of `sumo-qa-reviewing-before-merge` (load via `sumo_qa_load_skill_context` with `mode="module"`). **Load when:** the host supplies a repo-map / diff-impact result, a context bundle, or a coverage/mutation artifact. **Extends:** checklist step 1 (read the diff). The root's Iron Law, verdict gate, and output discipline apply unchanged.

## Repo-map, context bundle, and coverage/mutation artifacts (step 1)

**Repo-map accelerator (optional).** `sumo_qa_analyze_diff_impact` scans live and persists a repo-map (`persisted_map_path`) when none exists, so a risk surface is never just "no repo-map / not scanned". It returns changed/affected nodes, likely tests, and the risk surface (changed sources with no mapped test); never blocks the review. **It is NOT coverage evidence** — `related_tests` are run-candidates, `risk_surface` candidate UNCOVERED anchors, never proof. If `probable_mapping_gap` is true (tests exist but the map found no links — e.g. CamelCase/Kotlin), the risk surface is a *mapping* gap, not zero coverage — confirm via the test tree. The Iron Law's fresh-run requirement is unchanged.

**Context bundle (optional input).** If the host hands you a context bundle — a compact, host-neutral record of issue/PR summary, changed files, test/CI evidence (each with a source + freshness marker), and user constraints — PREFER it as a head-start: validate and read it via `sumo_qa_format_context_bundle` (pass the live local head as `local_head_sha` so the tool flags a conflict). No bundle → fall back to direct repo inspection (root steps 1-2); the bundle is an accelerator, never a requirement, with no GitHub/network dependency. Three rules: (a) **stale/unknown evidence is not fresh evidence** — the bundle's CI/test facts are input, never the verdict source; any fact in the tool's `untrustworthy_evidence_fields` (freshness `stale`/`unknown`/`absent`) is treated as stale, so re-run the suite this turn and never claim safety from it; (b) **call out conflicts** — when the tool returns a `conflict` (bundle `head_sha` ≠ live local head), say so and trust the live diff you can inspect, overriding neither side silently; (c) **the bundle never replaces the diff read** — still read the actual diff and changed files (steps 1–2).

**Coverage/mutation artifacts (optional input).** A local coverage or mutation result the repo emitted (any format the host can read — a Cobertura `coverage.xml`, an `lcov.info`, a `coverage.json`, a Stryker/PIT/mutmut report) is SUPPORTING evidence: read it with the host's file tools, scoped to the CHANGED files/functions, never as a global vanity total. It is ASYMMETRIC, like the repo-map above — an uncovered or weakly-covered CHANGED line/function it names is a CANDIDATE risk you feed into the discovery sweep (step 4) and map UNCOVERED in the ledger (step 9); but a line the artifact calls "covered/executed", or a high coverage %, is NEVER proof a risk's failure path is exercised and NEVER a safe-to-merge criterion on its own (high coverage ≠ low risk). Only a fresh path-matching test with a verbatim assertion discharges a risk — the Iron Law is unchanged. Absent ⇒ emit the root's pinned one-liner (checklist step 1) and rest the verdict on risk coverage. These are the same signals the optional readiness scorecard consumes "only when they actually ran".

## Red Flags

| Thought | Reality |
|---|---|
| "Coverage report shows 96% on the changed file — SAFE" | A coverage % / artifact is SUPPORTING evidence, never a safe-to-merge criterion; high coverage ≠ low risk. It can RAISE an uncovered-changed-line risk into the sweep (step 4), but only a fresh path-matching test discharges one — a line marked "covered/executed" is not proof its failure mode is asserted. Absent ⇒ "not measured", rest on risk coverage. |
